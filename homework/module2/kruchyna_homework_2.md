## Завдання 1. Аналіз відкритих портів

### Команди

```bash
# Linux:
ss -tuln

# macOS-еквівалент (TCP у стані LISTEN та UDP-сокети):
netstat -anv -p tcp | grep LISTEN
netstat -anv -p udp
```

Для чистоти експерименту додатково запущено тестовий веб-сервер, як радить підказка:

```bash
python3 -m http.server 8080
```

### Результат (скорочено, залишено показові рядки)

```
Proto  Recv-Q Send-Q  Local Address          Foreign Address        (state)
tcp46       0      0  *.8080                 *.*                    LISTEN
tcp6        0      0  ::1.6379               *.*                    LISTEN
tcp4        0      0  127.0.0.1.6463         *.*                    LISTEN
tcp46       0      0  *.15611                *.*                    LISTEN
udp46       0      0  *.5353                 *.*
udp4        0      0  *.64901                *.*
```

У виводі `netstat` стовпець `(state)` для UDP порожній: UDP не має станів, бо не встановлює з'єднання.
У Linux `ss` для таких сокетів пише `UNCONN`.

### Аналіз

| Протокол | Порт | Стан | Що це |
|---|---|---|---|
| TCP | 8080 | LISTEN | `python3 -m http.server` — тестовий HTTP-сервер, слухає на всіх адресах (`*`) |
| TCP | 6379 | LISTEN | Redis (локальна база, тільки `::1` / `127.0.0.1`) |
| TCP | 6463 | LISTEN | Discord RPC-сервер (тільки `127.0.0.1`) |
| TCP | 15611 | LISTEN | Postman (локальний агент) |
| UDP | 5353 | UNCONN | mDNS / Bonjour (multicast DNS, виявлення пристроїв у локальній мережі) |

`LISTEN` означає, що процес відкрив порт і чекає вхідних TCP-з'єднань. Адреса `127.0.0.1` / `::1` означає,
що порт доступний лише з цього ж комп'ютера, а `*` (`0.0.0.0`) — з будь-якого інтерфейсу, у тому числі з мережі.

## Завдання 2. Аналіз процесів, що слухають порти

### Команди

```bash
# Linux:
ss -tulpn

# macOS-еквівалент:
lsof -nP -iTCP -sTCP:LISTEN    # TCP-сокети у стані LISTEN з процесом і PID
lsof -nP -iUDP                 # UDP-сокети
```

### Результат (скорочено)

```
COMMAND     PID  USER   FD   TYPE  NODE NAME
Python    63703 user     4u  IPv6  TCP *:8080 (LISTEN)
redis-ser 58147 user     6u  IPv4  TCP 127.0.0.1:6379 (LISTEN)
redis-ser 58147 user     7u  IPv6  TCP [::1]:6379 (LISTEN)
Discord   59223 user    38u  IPv4  TCP 127.0.0.1:6463 (LISTEN)
Postman   55582 user    82u  IPv6  TCP *:15611 (LISTEN)
Google    58922 user    76u  IPv4  UDP *:5353
```

### Аналіз

| Процес | PID | Порт | Протокол |
|---|---|---|---|
| `Python` (`http.server`) | 63703 | 8080 | TCP |
| `redis-server` | 58147 | 6379 | TCP |
| `Discord` | 59223 | 6463 | TCP |
| `Google Chrome` | 58922 | 5353 | UDP |

Стовпець `FD` — номер файлового дескриптора сокета в процесі (у Linux `ss -p` показує його як `fd=N`).
Запускати через `sudo` не знадобилось: усі перелічені процеси належать поточному користувачу, тому `lsof`
бачить їх без підвищених прав. Для системних процесів (`root`) імена були б приховані без `sudo`, як і в Linux.

## Завдання 3. Перевірка TCP-з'єднання

### Команда

```bash
nc -vz google.com 80
```

### Результат

```
Connection to google.com port 80 [tcp/http] succeeded!
```

### Аналіз

- **Чи встановлюється TCP-з'єднання:** так. `nc` виконав повний TCP handshake (SYN → SYN-ACK → ACK)
  і одразу закрив з'єднання (прапорець `-z` — «zero I/O», лише перевірка порту без передачі даних).
- **Порт:** 80, стандартний порт HTTP. Прапорець `-v` виводить результат, `[tcp/http]` — назва сервісу
  з `/etc/services`.

## Завдання 4. Порівняння TCP vs UDP

### Команди та результат

```bash
nc -vz 8.8.8.8 53
```
```
Connection to 8.8.8.8 port 53 [tcp/domain] succeeded!
```

```bash
nc -u -vz 8.8.8.8 53
```
```
Connection to 8.8.8.8 port 53 [udp/domain] succeeded!
```

Контрольний експеримент на порту, який у 8.8.8.8 точно закритий:

```bash
nc -vz -w 3 8.8.8.8 5300
```
```
nc: connectx to 8.8.8.8 port 5300 (tcp) failed: Operation timed out
```

```bash
nc -u -vz -w 3 8.8.8.8 5300
```
```
Connection to 8.8.8.8 port 5300 [udp/hacl-hb] succeeded!
```

### Аналіз

| | TCP (`nc -vz`) | UDP (`nc -u -vz`) |
|---|---|---|
| Відкритий порт 53 | `succeeded` — сервер відповів SYN-ACK, handshake відбувся | `succeeded` — але це лише факт, що датаграму відправлено |
| Закритий порт 5300 | `failed: Operation timed out` — SYN-ACK не прийшов | `succeeded` — хоча порт закритий |

- **TCP** — протокол з встановленням з'єднання (connection-oriented). «succeeded» означає реальне
  підтвердження від віддаленого хоста: він прийняв SYN і відповів SYN-ACK. Якщо порт закритий або
  відфільтрований, з'єднання не встановиться (RST або таймаут).
- **UDP** — протокол без з'єднання (connection-less). Handshake відсутній, `nc` просто відправляє датаграму
  і, не отримавши ICMP «port unreachable» за час очікування, вважає порт відкритим. Тому «succeeded» для UDP
  не гарантує, що на тому боці хтось слухає: експеримент із закритим портом 5300 це наочно показує
  (Google не надсилає ICMP-помилки, тож UDP-перевірка завжди «успішна»).
- **Різниця в поведінці:** TCP встановлює сесію і дає гарантію доставки та порядку пакетів, тому відповідь
  `nc` для TCP є достовірною. UDP не встановлює сесію і не гарантує відповіді, тому для перевірки UDP-сервісу
  потрібно відправити реальний запит протоколу (наприклад, DNS-запит через `dig`) і дочекатись відповіді.

## Завдання 5. DNS-резолвінг

Замість `google.com` використано домен `github.com`.

### Команди та результат

```bash
nslookup github.com
```
```
Server:		2a00:11b4:xxxx::x
Address:	2a00:11b4:xxxx::x#53

Non-authoritative answer:
Name:	github.com
Address: 140.82.121.4
```

```bash
dig github.com
```
```
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 26030
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; ANSWER SECTION:
github.com.		46	IN	A	140.82.121.4

;; Query time: 16 msec
;; SERVER: 2a00:11b4:xxxx::x#53(2a00:11b4:xxxx::x)
```

Та сама перевірка через DNS домашнього роутера:

```bash
nslookup github.com 192.168.0.1
```
```
Server:		192.168.0.1
Address:	192.168.0.1#53

Non-authoritative answer:
Name:	github.com
Address: 140.82.121.4
```

### Аналіз

- **Домен:** `github.com`
- **IP-адреса:** `140.82.121.4` (A-запис, TTL 46 секунд на момент запиту)
- **DNS-сервер, який відповів:** `2a00:11b4:xxxx::x` (порт 53) — IPv6-резолвер інтернет-провайдера, який
  система отримала через DHCPv6 / Router Advertisement і поставила першим у списку (`scutil --dns`). Другим
  резервним резолвером у списку стоїть домашній роутер `192.168.0.1`; при явному запиті до нього він повертає
  ту саму адресу.
- `Non-authoritative answer` означає, що відповідь дав кешуючий резолвер, а не авторитетний сервер зони
  `github.com`. Прапорці `qr rd ra` у `dig`: відповідь (`qr`), рекурсія запитана (`rd`) і доступна (`ra`).
- `status: NOERROR` — домен існує і запис знайдено; `Query time: 16 msec` — відповідь прийшла з кешу
  провайдера, тому дуже швидко.
