### Аналіз

**Послідовність прапорців перших трьох пакетів:**

| # | Напрямок | Flags | Що відбувається |
|---|---|---|---|
| 1 | клієнт → сервер | `[S]` | SYN: клієнт пропонує з'єднання, оголошує свій початковий seq `4054206760`, MSS, window scale, SACK |
| 2 | сервер → клієнт | `[S.]` | SYN+ACK: сервер погоджується, оголошує свій seq `1419629571` і підтверджує клієнтський (`ack 4054206761` = seq+1) |
| 3 | клієнт → сервер | `[.]` | ACK: клієнт підтверджує seq сервера (`ack 1` — tcpdump далі показує відносні номери). З'єднання встановлено |

**Чи відбувся успішний handshake:** так. Є повна трійка `[S]` → `[S.]` → `[.]` за 17,7 мс (RTT до
example.com), і одразу після неї клієнт надсилає дані (`GET / HTTP/1.1`), що можливо лише у встановленому
з'єднанні. Подальші пакети це підтверджують: сервер відповів `HTTP/1.1 200 OK`, після чого обидві сторони
коректно закрили з'єднання через `[F.]` (FIN+ACK) з кожного боку.

**Що означає `[P.]` (PSH+ACK).** Крапка — це ACK (він є майже у всіх пакетах після handshake). `P` —
прапорець **PUSH**: відправник просить TCP-стек не буферизувати ці дані, а негайно передати їх застосунку
на приймальній стороні (і сам відправник теж не чекає заповнення буфера перед відправкою). Його ставлять на
останній сегмент логічного блоку даних — тут це цілий HTTP-запит (пакет 4, `length 75`: `GET / HTTP/1.1`
із заголовками) і ціла HTTP-відповідь (пакет 6, `length 935`: `200 OK` + HTML). Пакети `[.]` без `P` між
ними — чисті підтвердження з `length 0`, даних не несуть. Без PUSH приймач міг би затримати дані в буфері,
чекаючи ще сегментів, що для інтерактивного протоколу «запит–відповідь» додало б затримку.

## Завдання 2. Налаштування Reverse Proxy (Nginx)

```nginx
location /api {
    proxy_pass http://localhost:3000;
    proxy_set_header X-Real-IP $remote_addr;
}
```

### Навіщо `proxy_set_header X-Real-IP`

Nginx як reverse proxy **сам встановлює нове TCP-з'єднання** до бекенда на `localhost:3000`. Для бекенда
клієнтом цього з'єднання є Nginx, тому в `remote_addr` (у коді — `req.ip`, `request.remote_addr`,
`$_SERVER['REMOTE_ADDR']` тощо) бекенд побачить `127.0.0.1`, а не адресу реального користувача. Наслідки
без заголовка:

- логи й аналітика показують одну адресу для всіх користувачів;
- rate limiting / anti-brute-force на бекенді блокує «127.0.0.1», тобто всіх одразу;
- geo-IP, аудит безпеки, виявлення підозрілих входів не працюють;
- блокування за IP неможливе.

Директива додає до проксійованого запиту заголовок `X-Real-IP: <IP клієнта>` (змінна `$remote_addr` —
адреса того, хто підключився до Nginx). Бекенд читає його і отримує справжню адресу. Часто поруч ставлять
`X-Forwarded-For` (увесь ланцюжок проксі), `X-Forwarded-Proto` (http/https) і `Host`.

Важлива умова: бекенд має довіряти `X-Real-IP` **лише** від Nginx (наприклад, приймати з'єднання тільки з
`127.0.0.1`), інакше зловмисник, діставшись до порту 3000 напряму, підставить будь-яку адресу.

### Перевага безпеки `proxy_pass` замість відкриття порту 3000

Порт 3000 слухає лише на `localhost` і з інтернету недоступний; єдина публічна точка входу — Nginx на
80/443. Це дає:

- **Менша поверхня атаки.** Node/Python/Go-сервери застосунку не призначені бути «фронтом» в інтернет:
  повільніше обробляють некоректні запити, частіше мають вразливості парсингу. Nginx — загартований
  HTTP-сервер, який відсікає сміття до того, як воно дійде до коду застосунку.
- **Термінація TLS в одному місці.** Сертифікати, сучасні шифри, HSTS налаштовуються один раз на Nginx;
  бекенд працює по звичайному HTTP у локальній мережі.
- **Фільтрація та ліміти.** `limit_req`, `limit_conn`, `client_max_body_size`, таймаути, блокування за
  IP/геолокацією, базовий захист від повільних DoS (slowloris) — усе на проксі.
- **Приховування деталей.** Клієнт не бачить, яка технологія і версія за `/api`, скільки інстансів, на яких
  портах. Заголовок `Server` і внутрішні помилки можна приховати.
- **Контроль маршрутів.** Назовні відкрито лише `/api`; службові ендпоїнти (`/metrics`, `/debug`,
  `/admin`) можна залишити недоступними, навіть якщо бекенд їх віддає.
- **Централізовані логи та аудит** одного входу замість кількох сервісів.
- **Місце для WAF.** Модуль ModSecurity/NAXSI на Nginx аналізує запити до того, як вони дійдуть до бекенда.

## Завдання 3. Вибір алгоритму балансування

**Умова:** сесії зберігаються у локальній пам'яті конкретного сервера (stateful).

**Вибір: IP Hash** (у Nginx — `ip_hash;` у блоці `upstream`).

### Обґрунтування

IP Hash обчислює хеш від IP-адреси клієнта і за ним детерміновано обирає сервер. Усі запити одного клієнта
потрапляють на **той самий** бекенд, поки він живий, — а саме там лежить його сесія. Це найпростіший спосіб
забезпечити *session affinity* (sticky sessions) без змін у застосунку.

### Яка проблема з Round Robin

Round Robin розподіляє запити по колу: 1-й — на сервер A, 2-й — на B, 3-й — на C, незалежно від того, хто
їх надіслав. Сценарій:

1. Користувач логіниться, запит потрапляє на сервер A, A створює сесію у своїй пам'яті і віддає cookie
   `session_id`.
2. Наступний запит того ж користувача Round Robin відправляє на сервер B. B шукає `session_id` у **своїй**
   пам'яті, не знаходить → користувач «розлогінений», кошик порожній, форма втратила дані.
3. Третій запит іде на C — те саме. Користувач бачить хаотичну поведінку: то залогінений, то ні.

Least Connections має ту саму проблему: він обирає найменш завантажений сервер, а не «той, де сесія».

### Обмеження IP Hash і що краще в довгостроковій перспективі

- Багато користувачів за одним NAT (офіс, мобільний оператор) мають одну публічну IP → усі потрапляють на
  один сервер, розподіл стає нерівномірним.
- Клієнт зі змінною IP (перемикання Wi-Fi ↔ LTE) втрачає сесію.
- Падіння сервера все одно втрачає сесії його користувачів.

Тому IP Hash — коректна відповідь для **поточної stateful-архітектури**, але правильний довгостроковий крок —
винести сесії у спільне сховище (Redis) або в підписаний токен (JWT), зробити сервери stateless і тоді
вільно використовувати Round Robin / Least Connections. Проміжний варіант — cookie-based sticky sessions
(`sticky cookie` у Nginx Plus, HAProxy `cookie SERVERID insert`), які прив'язують сесію до сервера точніше,
ніж IP.

## Завдання 4. Мікросегментація в Kubernetes

```yaml
spec:
  podSelector:
    matchLabels:
      app: database
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: backend
```

### До яких Pod-ів застосовується правило

До всіх Pod-ів з міткою `app: database` **у тому namespace, де створено NetworkPolicy** (NetworkPolicy —
namespaced-об'єкт, `podSelector` не виходить за його межі). Це «цільові» Pod-и: саме їхній вхідний трафік
політика обмежує. Оскільки в `spec` є секція `ingress`, а `policyTypes` не вказано, політика діє на
**вхідний** трафік; вихідний (egress) з бази вона не чіпає.

### Яким Pod-ам дозволено доступ до бази

Лише Pod-ам з міткою `app: backend` з **того самого namespace** (у `from` вказано тільки `podSelector`
без `namespaceSelector`, тому інші namespace не підпадають). Дозволено на **всі порти**, бо секція `ports`
відсутня.

Ключовий момент семантики NetworkPolicy: щойно до Pod-а застосовано хоча б одну політику з типом Ingress,
він переходить у режим **default deny** для вхідного трафіку — дозволено лише те, що явно перелічено в
union усіх політик. Отже заблоковано:

- `app: frontend` та будь-які інші Pod-и цього namespace;
- усі Pod-и з інших namespace, навіть з міткою `app: backend`;
- трафік ззовні кластера.

Умова роботи: у кластері має бути CNI-плагін, що реалізує NetworkPolicy (Calico, Cilium, Weave,
Antrea…). Flannel без доповнень політики ігнорує — об'єкт створиться, але нічого не обмежить.

### Як це обмежує Blast Radius при зломі фронтенда

Фронтенд — найбільш відкрита частина системи: приймає трафік з інтернету, рендерить користувацький ввід,
тягне багато залежностей. Припустимо, зловмисник через вразливість (RCE в npm-пакеті, SSRF, витік
credentials) отримав shell у Pod-і `app: frontend`.

**Без NetworkPolicy** (плоска мережа Kubernetes за замовчуванням) з цього Pod-а доступний будь-який інший Pod
кластера, у тому числі база даних на `database:5432`. Далі — підбір/крадіжка пароля з env-змінних чи
ConfigMap, дамп усіх даних. Один скомпрометований контейнер = скомпрометовані дані всієї системи.

**З цією політикою** пакети від `frontend` до `database` відкидаються на рівні CNI (eBPF/iptables на ноді),
ще до того, як дійдуть до порту бази. Зловмисник у фронтенді:

- не може навіть просканувати базу (порт для нього «не існує»);
- має шукати наступну вразливість — тепер уже в `backend`, який є додатковим бар'єром зі своєю
  валідацією, авторизацією та логуванням;
- залишає сліди: спроби з'єднань з `frontend` на `database` — аномалія, яку логує CNI (Cilium Hubble,
  Calico flow logs) і яка одразу підіймає алерт.

Це і є мікросегментація / zero trust усередині кластера: доступ дозволено не «всім у мережі», а лише тим
ролям, яким він потрібен за архітектурою (`backend → database`). Радіус ураження (blast radius) обмежується
одним шаром замість усієї системи. Логічне продовження — аналогічна політика для `backend` (ingress лише від
`frontend` і лише на порт API), egress-політики (щоб скомпрометований Pod не міг відправити дані назовні або
на metadata-сервіс хмари), і `default deny` для всього namespace.

## Завдання 5. Аналіз системи виявлення вторгнень (IDS)

Подія: `[Alert] ET EXPLOIT POSSIBLE SQL Injection (UNION SELECT)` — сигнатура з набору Emerging Threats
спрацювала на HTTP-запит, у якому в параметрі є конструкція `UNION SELECT` (класична спроба витягти дані
з інших таблиць через SQL-ін'єкцію).

### IDS vs IPS: що б зробила IPS

**IDS (Intrusion Detection System)** працює *поза* трафіком: отримує копію пакетів (SPAN/mirror-порт або
TAP), аналізує і **лише повідомляє** — пише alert у лог / SIEM, надсилає сповіщення. Пакет уже дійшов до
веб-сервера, і якщо застосунок вразливий, ін'єкція **виконалась**. Реакція — ручна або через інтеграцію
(SOAR, блок на firewall), але із затримкою.

**IPS (Intrusion Prevention System)** стоїть *у розриві* (inline): кожен пакет проходить через неї до того,
як потрапить до сервера. Та сама Suricata у режимі IPS (`af-packet` inline, NFQUEUE або через firewall з
`drop`-правилом) при спрацюванні сигнатури зробила б:

1. **Drop** — відкинула б пакет із `UNION SELECT`; запит до веб-сервера не дійшов би взагалі.
2. Зафіксувала подію як `[Drop]` замість `[Alert]` у `eve.json`/`fast.log`.
3. Залежно від конфігурації — **reject** (надіслати TCP RST обом сторонам, щоб закрити з'єднання) і/або
   додати IP джерела до тимчасового блок-списку на N хвилин.

Різниця в наслідках: IDS → атака відбулась, є запис для розслідування; IPS → атака не дійшла до цілі.
Ціна IPS — вона стає точкою відмови й вузьким місцем за продуктивністю, а хибне спрацювання (false positive)
означає заблокований легітимний користувач (наприклад, юрист, який у формі пошуку написав «union select»
у тексті документа). Тому сигнатури для IPS тюнять обережніше.

### Додатковий рівень захисту (Defense in Depth), ближчий до edge

**WAF (Web Application Firewall) на edge** — наприклад, Cloudflare WAF, AWS WAF перед CloudFront/ALB,
ModSecurity з OWASP Core Rule Set на reverse proxy. WAF розуміє HTTP на рівні застосунку: декодує URL,
парсить параметри, тіло JSON/форми, cookie і застосовує правила класу «SQLi» (CRS правило 942xxx) з
оцінкою аномалії. Запит із `' UNION SELECT username,password FROM users--` був би заблокований ще на
CDN/edge-ноді провайдера, за тисячі кілометрів від нашої мережі, і Suricata взагалі не побачила б цього
трафіку. Едж-WAF до того ж:

- термінує TLS, тому бачить розшифрований запит (мережева IDS без розшифрування бачить лише метадані HTTPS);
- не залежить від пропускної здатності нашого каналу та не стає вузьким місцем;
- отримує сигнатури та reputation-дані (відомі ботнети, Tor-exit, сканери) від провайдера в реальному часі.

Повний ланцюжок шарів у концепції Defense in Depth для цієї атаки виглядає так, і кожен шар не залежить від
попереднього:

| Шар | Де зупиняє | Приклад |
|---|---|---|
| Edge / CDN | до входу в нашу мережу | WAF, rate limiting, geo/IP reputation, bot management |
| Периметр | на вході в мережу | NGFW, IPS inline (Suricata у режимі drop) |
| Мережа всередині | між сегментами | NetworkPolicy / мікросегментація (завдання 4), IDS на SPAN |
| Хост / застосунок | у коді | параметризовані запити (prepared statements), ORM, валідація вводу — єдине, що усуває вразливість, а не лише блокує експлойт |
| Дані | навіть при успішній ін'єкції | обліковий запис БД з мінімальними правами (без `DROP`, без доступу до чужих таблиць), шифрування чутливих полів |
| Виявлення та реагування | після факту | SIEM, алерти, аудит запитів БД, план реагування |

Найважливіший шар тут усе ж найглибший — параметризовані SQL-запити: якщо вразливості немає, `UNION SELECT`
у параметрі — просто рядок, а не команда. Усі інші шари зменшують імовірність і масштаб шкоди, поки
вразливість існує або ще не виявлена.
